## 2. 材料预处理（为什么必须做）

Dify「通用分段」会**自己解析 Markdown 结构**（标题行、有序列表、表格、空行），把本该连在一起的「标题 + 列表正文」拆成多个只有几字的段落。实测后果：检索能召回「学习目标」这个标题，但 6 条学习目标正文落在别的段落里，模型只能看到孤零零的标题。

处理方式（脚本已入库）：[`tools/build_knowledge_base_materials.py`](../tools/build_knowledge_base_materials.py)

```powershell
python tools/build_knowledge_base_materials.py
```

脚本把 `materials/*.md` 转成 `materials_v3/*.md`：

1. 剥离全部 Markdown 标记（`#`、列表符、表格竖线、`**`、行内代码、链接、引用）；
2. 按 `#`/`##`/`###` 标题分节，**一节合并为一段**；
3. 段内换行压成空格，**段落内部不含 `\n`**，使 Dify 只能按空行切段。

转换后逐份自检（段数 / 最短 / 最长 / 平均 / 是否残留 `#`），输出的段数与 Dify 知识库「分段列表」中实际索引的段数一致。

> `materials/` 与 `materials_v3/` 都**不入 Git**（`.gitignore` 已排除）：前者是课程资料原文，后者是它的纯文本改写版，二者同属「不随交付包再分发」的内容。重建时由刘英超按授权提供 `materials/`，再跑上面的脚本即可复现 `materials_v3/`。

## 4. 原文获取方式

原文**不随交付包分发**（体积大、涉及引用授权）。获取方式二选一：

1. 由刘英超按授权私下提供 `materials/` 下 6 个 Markdown 文件；对方用 `documents.csv` 的 SHA-256 校验一致性；
2. 在部署服务器上查看 Dify 容器内已上传文档（`docker compose exec api ls /app/api/storage/upload_files`），导出后重新入库。

拿到原文后必须先用 SHA-256 核对，避免用不同版本重建导致 `evidence.csv` 的行号/页码错位。

## 5. 重建步骤

1. **准备材料**：把 `materials/` 放到仓库根目录，执行 `python tools/build_knowledge_base_materials.py`，确认 6 份文件的段数分别接近 18 / 23 / 20 / 24 / 34 / 25。
2. **配置模型供应商**：设置 → 模型供应商 → 硅基流动，填入 API Key（Key 只在平台配置，不写进任何文件）。
3. **新建知识库**：知识库 → 创建知识库 → 上传 `materials_v3/` 下 6 个 `.md` → 分段设置选「通用」（块长/重叠保持默认即可，材料段内无换行，不会被二次切分）。
4. **选择索引**：高质量（向量）索引，Embedding 选 `BAAI/bge-m3`，保存并等待索引完成。
5. **核对分段**：打开任一份文档的「分段列表」，确认「学习目标」段包含完整 6 条，而不是只有一个标题。
6. **重新绑定工作流**：打开应用「课程问答证据核验」→ 知识检索节点 → 重新选择新建的知识库（`dataset_id` 会变）→ 确认 `top_k=8`、无分数阈值。
7. **发布**：保存并发布新版本，用「这门课有哪些学习要求？」做一次预览，确认返回 `overall_status` 非空、`evidence_count > 0`、`error_code` 为 `null`，且引用的原文是完整段落。
8. **回归**：跑 `python evaluation/run_questions.py --ids Q01,Q17,Q25` 抽三题，确认三类题目（有答案 / 无答案 / 歧义）行为正常。

## 6. 已知局限

- 知识库没有导出成文件包，Dify 1.19 也不提供完整索引备份；只能在原环境保留或按上文重建。
- 检索节点面板上的「混合检索权重」在本机 UI 自动化下改不动，实测 `keyword_weight=0, vector_weight=1`，即实际等价于纯向量检索；要提高关键词召回需在浏览器 DevTools 里直接改请求，或接受纯向量。
- 30 题对照实验是在旧知识库（top_k=5、Markdown 原文入库）上跑的；改成纯文本材料 + top_k=8 后只做了抽题验证（Q01/Q17/Q25 与 3 道学习要求题），未重跑全量 30 题。
