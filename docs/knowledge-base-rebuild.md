## 3. 原文获取方式

原文**不随交付包分发**（体积大、涉及引用授权）。获取方式二选一：

1. 由刘英超按授权私下提供 `materials/` 下 6 个 Markdown 文件；对方用 `documents.csv` 的 SHA-256 校验一致性；
2. 在部署服务器上查看 Dify 容器内已上传文档（`docker compose exec api ls /app/api/storage/upload_files`），导出后重新入库。

拿到原文后必须先用 SHA-256 核对，避免用不同版本重建导致 `evidence.csv` 的行号/页码错位。

## 4. 重建步骤

1. **配置模型供应商**：设置 → 模型供应商 → 硅基流动，填入 API Key（Key 只在平台配置，不写进任何文件）。
2. **新建知识库**：知识库 → 创建知识库 → 上传 6 个 `.md` → 分段设置选「通用」，建议块长 512、重叠 50（与原库一致时请以实际分段页为准）。
3. **选择索引**：高质量（向量）索引，Embedding 选 `BAAI/bge-m3`，保存并等待索引完成。
4. **核对文档数**：应为 6 份、状态全部「已索引」。
5. **重新绑定工作流**：打开应用「课程问答证据核验」→ 知识检索节点 → 重新选择新建的知识库（`dataset_id` 会变）→ 确认 top_k=5、无阈值。
6. **发布**：保存并发布新版本，用「什么是 KV Cache？」做一次预览，确认返回 `overall_status` 非空、`evidence_count > 0`、`error_code` 为 `null`。
7. **回归**：跑 `python evaluation/run_questions.py --ids Q01,Q17,Q25` 抽三题，确认三类题目（有答案 / 无答案 / 歧义）行为正常。

## 5. 已知局限

- 知识库没有导出成文件包，Dify 1.19 也不提供完整索引备份；只能在原环境保留或按上文重建。
- 分块参数未留档，重建后片段边界可能与原库不同，检索结果会有差异；这也是 3 道题（Q06/Q08/Q13）漏答的原因之一（相关段落未被 top_k=5 召回）。
- 若要提升召回，优先调整 top_k（5 → 8）或改分块，而不是换更大的模型。
